## 0. What we are building

We are building **Puregram
Control**: a complete, professional, real-time web app where a **manager**
(e.g. a parent) controls which Telegram chats a **managed** account (e.g. a
child, on the Puregram fork device) is allowed to open. The fork already polls
`telegram_whitelist` per device and enforces it; we are building the human
front-end + the API + the public site around it.

Decisions (locked):
- **Auth:** email + password (Argon2id). Independent of Telegram. No bot login.
- **Bot:** retired. `Puregram Control` (web app) fully replaces it.
- **Control UI stack:** React + TypeScript (strict) + Vite + Tailwind CSS, built
  to static files, served by nginx at `https://puregram.app/app/`.
- **Real-time sync:** Server-Sent Events (SSE) from the FastAPI backend.
- **Bilingual** Arabic (default, RTL) + English (LTR). Dark + light themes.

## 3. Data model — schema additions (Agent 1 owns)

Apply idempotently on startup (CREATE … IF NOT EXISTS / ALTER … IF NOT EXISTS),
same style as `server/schema.sql`. Timestamps = zero-padded ISO-8601 UTC **TEXT**
(`to_char(now() AT TIME ZONE 'utc','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')`), so
lexicographic compare == chronological. psycopg uses `%s` placeholders. All
queries parameterized. Passwords = Argon2id (reuse `auth.hash_password`).

```sql
-- Control users (email/password accounts for the web app)
CREATE TABLE IF NOT EXISTS control_users (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email         TEXT UNIQUE NOT NULL,            -- normalized lower-case
    password_hash TEXT NOT NULL,                   -- Argon2id
    display_name  TEXT,
    lang          TEXT NOT NULL DEFAULT 'ar' CHECK (lang IN ('ar','en')),
    tg_user_id    BIGINT,                          -- Telegram account this user owns (managed side)
    tg_verified   INTEGER NOT NULL DEFAULT 0,
    share_code    TEXT UNIQUE,                     -- random token, for linking by code
    created_at    TEXT NOT NULL DEFAULT to_char(now() AT TIME ZONE 'utc','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'),
    updated_at    TEXT NOT NULL DEFAULT to_char(now() AT TIME ZONE 'utc','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'),
    last_seen_at  TEXT
);
-- One Telegram account maps to at most one control user.
CREATE UNIQUE INDEX IF NOT EXISTS uq_control_users_tg
    ON control_users(tg_user_id) WHERE tg_user_id IS NOT NULL;

-- The manage graph between control users (manager controls managed).
CREATE TABLE IF NOT EXISTS control_links (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    manager_user_id  BIGINT NOT NULL REFERENCES control_users(id) ON DELETE CASCADE,
    managed_user_id  BIGINT NOT NULL REFERENCES control_users(id) ON DELETE CASCADE,
    status           TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','revoked')),
    created_at       TEXT NOT NULL DEFAULT to_char(now() AT TIME ZONE 'utc','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'),
    updated_at       TEXT NOT NULL DEFAULT to_char(now() AT TIME ZONE 'utc','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'),
    CHECK (manager_user_id <> managed_user_id),
    UNIQUE (manager_user_id, managed_user_id)
);
CREATE INDEX IF NOT EXISTS idx_control_links_mgr ON control_links(manager_user_id, status);
CREATE INDEX IF NOT EXISTS idx_control_links_mgd ON control_links(managed_user_id, status);

-- Consent: a manager requests to manage a target; the target approves in-app.
CREATE TABLE IF NOT EXISTS control_link_requests (
    id                BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    requester_user_id BIGINT NOT NULL REFERENCES control_users(id) ON DELETE CASCADE,
    target_user_id    BIGINT NOT NULL REFERENCES control_users(id) ON DELETE CASCADE,
    status            TEXT NOT NULL DEFAULT 'pending'
                      CHECK (status IN ('pending','approved','declined','cancelled')),
    created_at        TEXT NOT NULL DEFAULT to_char(now() AT TIME ZONE 'utc','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'),
    updated_at        TEXT NOT NULL DEFAULT to_char(now() AT TIME ZONE 'utc','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'),
    CHECK (requester_user_id <> target_user_id)
);
-- At most one pending request per (requester, target).
CREATE UNIQUE INDEX IF NOT EXISTS uq_link_req_pending
    ON control_link_requests(requester_user_id, target_user_id) WHERE status = 'pending';
```

The whitelist itself stays in the EXISTING tables: a managed user's
`tg_user_id` → `customers.tg_user_id` (their devices) → `telegram_known_chats`
(what they can see) + `telegram_whitelist`/`telegram_whitelist_meta.version`
(what's allowed; the fork polls the version). For `known_chats_for(tg_user_id)`
and the chat-toggle logic, write the whitelist row + bump version for EVERY
device of that account.

## 4. Control API contract (new, additive)

- Mounted in `server/app/main.py` behind nginx `/control/` (prefix stripped), so
  the app sees `/v1/control/...`. SPA base URL: `https://puregram.app/control/v1`
  (prod, same origin); dev `http://localhost:8020/v1` via Vite proxy.
- **Auth cookie:** `puregram_user` — HttpOnly, SameSite=Lax, `Secure` in prod,
  HS256 JWT signed with `settings.jwt_secret`, claim `{"sub":<id>,"typ":"user"}`,
  TTL `PUREGRAM_USER_JWT_TTL_HOURS` (default 720h = 30 days). Distinct from the
  admin cookie `puregram_admin`. Dependency `require_user` resolves it → 401 if
  missing/invalid. Reuse Argon2id helpers in `server/app/auth.py`.
- Errors: FastAPI default `{"detail": "..."}`; use correct status codes
  (201 create, 401 auth, 403 forbidden, 404 not found, 409 conflict, 422 validation).
- Login throttle: reuse the in-memory pattern from `routes/admin.py`.
- Write to `audit_log` for sensitive mutations (actor `'user'`).

**User profile object** (returned by auth/me endpoints):
```json
{ "id":1, "email":"a@b.com", "display_name":"Abu Omar", "lang":"ar",
  "tg_user_id":123456789, "tg_verified":false, "share_code":"PGU-xyz..." }
```

### Auth & profile
| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/v1/control/register` | `{email,password(min8),display_name?,lang?}` | sets cookie → user profile (201); 409 if email exists |
| POST | `/v1/control/login` | `{email,password}` | sets cookie → user profile; 401 invalid; 429 throttled |
| POST | `/v1/control/logout` | — | `{ok:true}`, clears cookie |
| GET | `/v1/control/me` | — | user profile (401 if not signed in) |
| PATCH | `/v1/control/me` | `{display_name?,lang?}` | updated profile |
| POST | `/v1/control/account/password` | `{current_password,new_password(min8)}` | `{ok:true}`; 401 if current wrong |

### Telegram account binding (managed side declares the account it owns)
| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/v1/control/me/telegram` | `{tg_user_id:int}` | updated profile; 409 if that tg id is bound to another user |
| DELETE | `/v1/control/me/telegram` | — | updated profile (unbinds) |

(Verification is self-declared for now; `tg_verified` stays false. Note a future
device-issued code in comments.)

### Linking (consent) — PANEL-INITIATED (2026-07-26)

Supervision UI was removed from both messenger forks. A link now starts in the
panel and is answered on the handset:

1. The supervisor enters the managed account's Telegram identity (`@username`,
   numeric id, or a t.me link — resolved against `customer_accounts`, the roster
   every device reports).
2. The server files a `control_link_requests` row with a short `code` and a
   30-minute `expires_at`, and returns the code to the panel.
3. The handset's whitelist loop polls `GET /v1/device/link-requests/pending` and
   raises a NOTIFICATION naming the supervisor and showing the same code, with
   Allow / Decline. No supervision screen or code ever appears in the app.
4. Allow → `POST /v1/device/link-requests/{id}/approve` (device-authed) creates
   the active `control_link`. Consent therefore still lives on the handset: the
   panel alone cannot link an account.

`code` is a VERIFICATION code, not a credential — approving requires the device
bearer token — so it is stored in plaintext and displayed on both sides.

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/v1/control/links/requests` | `{target:"@username \| tg id \| t.me/… \| email \| share_code"}` | `{id,code,expires_at,target:{id,display_name,email,tg_user_id,username}}`; re-sending to the same target returns the live request with a refreshed deadline; 404 unknown, 409 already linked, 422 self |
| GET | `/v1/control/links/requests/incoming` | — | `[{id,requester:{…},created_at}]` (pending, target=me) |
| GET | `/v1/control/links/requests/outgoing` | — | `[{id,target:{…},code,expires_at,created_at}]` (pending, requester=me; past-deadline rows are lapsed first) |
| POST | `/v1/control/links/requests/{id}/approve` | — | `{ok:true}` (web target only → creates active control_link) |
| POST | `/v1/control/links/requests/{id}/decline` | — | `{ok:true}` (target only) |
| POST | `/v1/control/links/requests/{id}/cancel` | — | `{ok:true}` (requester only) |

Device side (bearer token, `/v1/device/*`):

| Method | Path | Returns |
|---|---|---|
| GET | `/v1/device/link-requests/pending` | `{requests:[{id,code,expires_at,created_at,tg_user_id,supervisor:{display_name,email_masked}}]}` for every account on this device |
| POST | `/v1/device/link-requests/{id}/approve` | `{ok:true,status:"approved",supervisor:{…}}`; 403 not this device's account, 409 not pending, 410 expired |
| POST | `/v1/device/link-requests/{id}/decline` | `{ok:true,status:"declined"}` |

The device reports its identity on `POST /v1/device/telegram/chats` with
`{tg_user_id, tg_username, tg_name}` — that is what makes an account findable
from the panel.

### Links overview
| Method | Path | Returns |
|---|---|---|
| GET | `/v1/control/managed` | accounts I manage: `[{user_id,display_name,email,tg_user_id,username,tg_verified,known_count,allowed_count,last_seen_at}]` (allowed_count from the per-ACCOUNT whitelist; ordered by device last-seen) |
| GET | `/v1/control/managers` | people who manage me: `[{user_id,display_name,email,since}]` |
| DELETE | `/v1/control/managed/{user_id}` | unlink (I stop managing them) → `{ok:true}` |
| DELETE | `/v1/control/managers/{user_id}` | remove a manager over me → `{ok:true}` |

### Chats (manager controlling a managed account) — 403 unless manager of `{user_id}`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/v1/control/managed/{user_id}/chats` | — | `{tg_user_id,version,chats:[{chat_id,kind,title,username,allowed,last_seen_at}]}` (distinct across the account's devices, effective allowed; empty + version 0 if no tg bound) |
| PUT | `/v1/control/managed/{user_id}/chats/{chat_id}` | `{allowed:bool,kind?,label?}` | `{ok:true,allowed,version}` |
| DELETE | `/v1/control/managed/{user_id}/chats/{chat_id}` | — | `{ok:true,allowed:false,version}` — explicit block, survives a re-report |
| POST | `/v1/control/managed/{user_id}/chats/bulk` | `{text}` | `{ok:true,added,skipped,version}` |

Writes go to `telegram_account_whitelist` keyed by `tg_user_id` — the table the
forks actually enforce via `GET /v1/device/telegram/whitelist/all` — and bump
`telegram_account_whitelist_meta.version`, so every device on the account picks
the change up within one poll (~15s).

### Real-time — SSE
`GET /v1/control/stream` → `text/event-stream`, authenticated (cookie). Per
connection, an async loop (poll DB every ~3s; single worker is fine) emits only
on change:
- `event: ping` — `data: {}` heartbeat every ~25s (keep-alive).
- `event: incoming` — `data:{"count":N}` when my pending incoming-request count changes.
- `event: outgoing` — `data:{"count":N}` when a request I sent is answered on a handset.
- `event: links` — `data:{"count":N}` when the number of accounts I supervise changes
  (this is what flips the panel's "waiting for approval" card to linked).
- `event: unlink_request` — `data:{"count":N}` pending unlink requests over my accounts.
- `event: chats` — `data:{"managed_user_id":M,"version":V}` when a whitelist
  version changes for an account I manage (so an open detail view re-fetches),
  and `data:{"self":true,"version":V}` when MY own account's whitelist changes.

Send an initial snapshot event on connect. Set headers `Cache-Control: no-cache`,
`X-Accel-Buffering: no`. The SPA uses `EventSource` (cookie travels same-origin).

## 5. Frontend (Agent 2) integration rules

- Vite `base: '/app/'`. Build to `app/dist/`. `npm run build` and `tsc --noEmit`
  must pass clean. Node ≥18.
- API base: `const API = import.meta.env.VITE_API_BASE ?? '/control/v1'`.
  All fetches `credentials:'include'`. A 401 → route to `/login`.
- Dev: `vite.config.ts` proxy `'/control' → 'http://localhost:8020'`
  (rewrite `^/control` → ''), so dev hits the real API shape.
- `EventSource('/control/v1/control/stream')` for live updates; reconnect on error.
- Routes (hash or history with `/app/` base): `/login`, `/register`, `/` (dashboard),
  `/managed` (accounts I manage), `/managed/:userId` (detail + live chat toggles),
  `/managers` (who manages me + incoming requests), `/link` (send a link request),
  `/settings` (profile, language, theme, bind Telegram id, change password).
- Bilingual i18n (ar default RTL / en LTR), theme toggle (dark default), the brand
  system in §2, the new logo. Production-quality: loading/empty/error states,
  optimistic toggles reconciled with the server version, toasts, accessible,
  responsive, keyboard-navigable. TypeScript everywhere (no `any`).

## 6. Conventions (all backend code)

- psycopg3 + pooled `dict_row`, `%s` placeholders, parameterized always.
- ISO-TEXT timestamps via the `utcnow_iso()` helper.
- Argon2id for passwords; never log secrets; secrets only from env.
- Keep functions small and single-responsibility; type hints everywhere.
- Mount new routers in `server/app/main.py`; keep CORS additions minimal
  (same-origin in prod; allow `http://localhost:5173` dev origin with credentials).
- Do not break existing device/admin/license/telegram-admin routes.
